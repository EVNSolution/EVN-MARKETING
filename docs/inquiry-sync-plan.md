# 문의 내역 연동 — 1차 개발 계획

작성일: 2026-09-14 · 갱신일: 2026-09-15 · 상태: 실문의 380건 보존, 신규 전용 수집 및 WARP 자동 등록 구현·검증 단계

실행 결과와 남은 확인은 [검증 기록](inquiry-sync-verification.md), 실행 방법은 [로컬 실행 안내](inquiry-sync-runtime.md)에 기록한다. 아래 내용은 승인된 개발 범위와 처리 원칙이다.

## 1. 이번 개발에서 완성할 결과

mleverage-admin에서 현재 계정으로 열람할 수 있는 이브이앤솔루션의 문의 내역을 우리 서비스로 가져온다. 최초에는 조회 가능한 과거 문의를 수집하고, 이후 1시간마다 새로 추가된 문의만 가져온다. 가져온 문의는 회사 WARP 고객관리로 자동 등록하며, 연락처가 기존 고객과 같으면 그 고객에 새 문의 이력을 추가한다. 로컬에서 먼저 검증한 뒤 상시 서버로 이전한다.

사용자에게 보여줄 원본 정보는 문의일자, 문의시간, 상담상태, 성함, 연락처다. 이름이 없는 전화 문의도 저장한다. 같은 사람이 여러 번 문의하면 각각의 문의를 보존한다.

기존 랜딩페이지와 알림톡은 현재 서비스를 통해 계속 운영한다. 자체 랜딩페이지, 광고 유입 추적, 알림톡 발송 구현, 내보내기, 원본 서비스에 수정 내용을 보내는 기능은 후속 범위다.

## 2. 확인된 사실과 남은 확인

| 항목 | 확인 내용 | 설계에 반영할 내용 |
| --- | --- | --- |
| 공급업체 연동 | 사용자 설명상 제공받을 API와 업체 협조 없음 | 로그인한 문의 화면을 읽는 수집 방식 |
| 표시 순번 | 같은 문의가 조회 기간에 따라 129와 6으로 달라짐 | 중복 판별에 사용하지 않음 |
| 원본 식별값 | 380건 전체에서 UUID 중복 없음. 2페이지 180건은 새로고침 후, 1페이지 200건은 페이지 왕복 후 모두 동일 | 회사·홈페이지 범위와 함께 저장 키로 사용. 이후 구조 변경은 실패로 감지 |
| 페이지 크기 | 200개 보기 선택 확인 | 수집은 최대 200개 단위, 실제 렌더링 완료를 확인하고 다음 페이지 이동 |
| 현재 확인한 범위 | 2000-01-01~2026-09-15 조회에서 380건, 200건+180건. 가장 오래된 표시 날짜는 2026-08-06 | 해당 조회 범위를 최초 수집 기준으로 사용. 삭제된 자료·접근 불가 자료·2000년 이전 자료의 존재 여부는 미확인 |
| 문의 형태 | 성함 공란 117건, 동일 연락처의 여러 문의 존재. 공란은 화면에서 `-` 표시 | 문의마다 별도 저장, 성함 필수 조건 없음 |
| 상담상태 | 원본 상태와 현재 CRM 고객 상태의 의미가 다름 | 원본 상담상태를 별도 보존 |
| 로그인 지속 시간 | 9월 14일 20:29 정상, 21:29 로그인 화면 관측 후 관찰 중단(KST) | 이 사이 재인증 필요. 정확한 자연 만료 시간·원인은 미확정 |

로그인 관찰은 시간마다 접속하는 조건의 측정이다. 유휴 상태에서의 만료 시간은 이 결과로 알 수 없다. 관찰 자동화는 제품의 문의 동기화 기능과 별개다.

9월 15일 원본 읽기 검증에서는 허가된 계정으로 재로그인하고 날짜·페이지 필터만 조작했다. 고객 이름·연락처는 검증 결과에 기록하지 않았다. 날짜는 `YYYY-MM-DD (요일)`, 시간은 `HH:mm`으로 표시된다. 별도 시간대 표기가 확인되지 않아 원본 날짜·시간을 변환 없이 보존한다.

## 3. 수집 흐름

`원본 로그인 확인 → 회사·홈페이지 범위 확인 → 조회 기간 설정 → 페이지별 읽기 → 식별값·필드 검증 → 저장 → 실행 결과 표시`

### 최초 수집

1. 날짜 필터의 기본값과 과거 조회 범위를 확인한다. 가장 오래된 문의 또는 조회 가능한 시작 범위를 확인하기 전에는 ‘전체 이관 완료’로 표시하지 않는다.
2. 대상 회사와 홈페이지를 고정하고 상담상태 전체로 조회한다. 삭제된 문의는 1차 수집 범위에서 제외한다.
3. 페이지당 200개로 읽되, 실제 행 내용과 페이지가 바뀌었는지 확인한다. 주소 변경만으로 조회 완료를 판단하지 않는다.
4. 내부 식별값 후보가 존재하고 페이지 전체에서 중복되지 않는지 검사한다. 식별값을 얻을 수 없는 행을 전화번호나 순번으로 임의 대체하지 않는다.
5. 성공적으로 읽은 페이지를 저장한다. 전체 조회가 끝난 뒤 건수와 고유 식별값 수를 대조한다.

### 매시간 수집

- 최신 문의부터 200개 단위로 읽는다. 마지막 성공 실행 이전에 이미 저장된 문의가 있는 페이지까지 확인하고 멈춘다. 신규가 없으면 첫 페이지 한 번만 읽는다.
- 처음 보는 원본 식별값만 추가한다. 기존 문의의 이름·연락처·상담상태는 다시 갱신하지 않는다.
- 신규가 200개를 넘으면 필요한 다음 페이지까지 읽는다. 다중 페이지에서는 첫 페이지의 식별값과 총수를 마지막에 한 번 더 확인하고, 경계가 변했으면 한 번 재시도한다.
- 중간 실패 중 저장된 문의는 다음 실행의 중단 기준으로 삼지 않는다. 마지막 성공 이전 자료에 도달할 때까지 계속 읽는다. 처음부터 성공 이력이 없다면 최초 전체 수집을 완료한다.
- 최신 날짜·시간 순서가 맞지 않으면 중단한다. 이 방식은 새 문의가 최신순 목록 앞에 추가된다는 조건을 사용하며, 오래된 날짜로 소급 삽입된 문의와 과거 수정은 정기 수집 대상이 아니다.

## 4. 저장과 변경 처리

원본은 로컬 `문의`와 `동기화 실행 기록`으로 보존한다. WARP 등록은 별도 인증 API로 전달하고, 로컬 문의에는 전달 시각·WARP 고객/이력 식별값·오류 코드만 추가 기록한다. 같은 서버에 배포하더라도 WARP DB를 직접 수정하지 않는다.

| 저장 대상 | 필요한 정보 |
| --- | --- |
| 문의 | 출처, 회사·홈페이지 범위, 원본 식별값, 문의일자, 문의시간, 상담상태, 성함, 연락처, 최초 수집 시각, 마지막 확인 시각 |
| 동기화 실행 기록 | 시작·종료 시각, 실행 상태, 읽은 건수, 신규·변경·동일 건수, 오류 유형 |

`출처 + 회사·홈페이지 범위 + 원본 식별값` 조합에 DB 중복 방지 제약을 둔다. 원본 식별값은 고객에게 보이는 순번과 별개다.

처리 규칙:

- 같은 문의를 열 번 읽어도 문의는 한 건이다.
- 같은 연락처·같은 분에 접수됐더라도 원본 식별값이 다르면 별도 문의다.
- 성함 공란과 원본의 상담상태 미선택을 그대로 표현한다. 가짜 이름이나 임의 상담상태를 넣지 않는다.
- 연락처는 원본 표시값을 보존한다. 검색용 표기 정리가 필요해도 원본을 덮어쓰지 않는다.
- 문의일자와 문의시간은 원본의 분 단위 정확도로 보존한다. 시간대는 화면 기준을 추가 확인해 명시하며, 읽기에 실패한 시각을 현재 시각으로 대체하지 않는다.
- 기존 원본 문의의 변경은 재수집하지 않는다. WARP의 기존 고객 상태, 메모, 담당자와 이름도 덮어쓰지 않는다.
- 원본에서 보이지 않게 된 문의를 자동 삭제하지 않는다. 삭제·필터 변경·일시적 누락을 한 번의 조회로 구분할 수 없기 때문이다.

WARP의 새 수신 API는 원본 식별값과 범위로 활동 ID를 결정한다. 같은 문의를 다시 보내면 기존 처리 결과를 반환한다. 기본 연락처에서 숫자만 남긴 값이 정확히 일치하는 고객이 한 명이면 이력만 추가하고, 없으면 B2C 잠재고객과 문의 이력을 만든다. 둘 이상이면 자동 선택하지 않고 오류로 보류한다. 기존 380건도 미등록 문의로 전달 대상에 포함한다. 자세한 운영 연결 조건은 [WARP 연동 안내](warp-integration.md)를 따른다.

## 5. 우리 서비스 화면

기존 로그인 안에 `문의 내역` 화면 하나를 추가한다.

- 표: 문의일자 / 문의시간 / 상담상태 / 성함 / 연락처. 기본 정렬은 최신 문의 순서.
- 조회: 날짜 범위, 상담상태, 성함·연락처 검색, 페이지 이동. 기본 20개, 최대 200개 보기.
- 상단: 마지막 수집 성공 시각, 현재 수집 상태, 최근 실행의 신규·기존 건수와 WARP 등록 완료·대기·오류 건수.
- 수동 실행: `지금 가져오기`. 자동 실행과 같은 수집·저장 흐름을 사용한다.
- 실패 안내: 로그인 필요, 조회 실패, 일부 수집, 화면 구조 변경을 구분한다. 이전에 저장한 문의는 계속 조회할 수 있다.

수집 설정·재로그인·수동 실행은 관리자 기능으로 설계하고 서버에서도 권한을 확인한다. 조회 화면은 기존 CRM의 접근 범위 안에 둔다. 기존 인증 흐름 전체를 개편하지 않는다.

## 6. 실행 환경과 실패 처리

로컬에서는 수집 프로세스 하나가 브라우저 세션을 유지하며 1시간 간격으로 실행한다. 자동·수동 실행은 동시에 돌지 않게 한다. 여러 작업자나 별도 작업 큐는 만들지 않는다.

| 상황 | 동작 |
| --- | --- |
| 최초 로그인·수집기 재시작 | Mac 키체인에 승인된 계정이 있으면 한 번 자동 로그인, 실패하거나 계정이 없으면 수동 로그인 대기 |
| 세션 만료·로그인 화면으로 이동 | 해당 실행을 중단하고 자동 재로그인 한 번 시도. 실패하면 로그인 필요 표시, 무한 재시도하지 않음 |
| 네트워크·페이지 로딩 실패 | 오류 유형만 기록하고 다음 정상 실행에서 다시 확인 |
| 중간 페이지 실패 | 이미 저장한 문의는 유지하고 ‘일부 수집’ 표시. 마지막 수집 성공 시각은 갱신하지 않음 |
| 로딩 화면 또는 빈 응답 | 정상 0건으로 처리하지 않음. 로딩 완료와 결과 수를 함께 확인 |
| 식별값·필수 열 구조 변경 | 영향을 받는 수집을 중단하고 확인 필요 표시 |
| Mac 잠자기·종료 또는 프로세스 종료 | 그동안 수집 불가. 재개 후 신규 수집 1회를 실행하며 밀린 횟수만큼 중복 실행하지 않음 |
| 수집 중 수동 실행 요청 | 진행 중인 실행을 표시하고 추가 실행하지 않음 |

로컬에서는 실행 중인 브라우저 세션을 재사용한다. 2026-09-16 사용자 요청에 따라 원본 비밀번호를 Mac 키체인에 보관하고 재시작·만료 시 자동 로그인한다. 비밀번호·토큰·쿠키를 소스, 출력, 로그, 캡처, 별도 평문 인증 파일에 저장하지 않는다. 서버의 자격 증명 주입 방식은 배포 환경에 맞춰 이후 설계한다.

고객 정보는 화면과 지정된 로컬 DB에만 보관하고, 테스트·에러 로그·보고서에는 실제 이름과 연락처를 넣지 않는다. 합성 데이터로 저장 로직을 먼저 검증한 뒤 사용자 요청 범위의 실제 문의를 연동한다.

## 7. 구현 순서와 통과 기준

| 순서 | 작업 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1 | 원본 읽기 검증 | 과거 조회 범위 확인, 여러 페이지의 식별값 안정성 확인, 이름 공란·시간·상태 추출 확인 |
| 2 | 문의 저장 구조와 반복 수집 처리 | 별도 임시 DB에서 데이터 보존형 변경 검증, 같은 자료 재처리 시 중복 없음 |
| 3 | 문의 조회 화면 | 다섯 필드의 표시·검색·필터·페이지 이동 및 로그인 보호 확인 |
| 4 | 시간당 실행과 복구 | 수동·자동 중복 실행 방지, 로그인 만료·중간 실패·재시작 처리 확인 |
| 5 | 실제 최초 수집과 대조 | 확인된 조회 범위의 고유 문의 건수 대조, 원본 필드 표본 대조, 연속 실행에서 중복 없음 |
| 6 | 로컬 운영 검증 | 신규 문의만 다음 성공 실행에 추가되고 기존 문의는 보존됨을 확인, 수집 시간·실패 유형 기록 |

2단계의 스키마 변경은 기존 DB의 초기화 없이 마이그레이션으로 준비한다. 기존 마이그레이션 이력 유무를 확인하고, 처음 만드는 경우 그 사실과 적용 범위를 보고한다. 이 계획 단계에서는 마이그레이션을 실행하지 않는다.

최소 자동 검증에는 다음을 묶는다: 동일 자료 두 번 처리, 같은 연락처의 별도 문의, 원본 상태 변경 무시, 성함 공란, 잘못된 날짜·시간, 200건 초과 페이지 이동, 중간 실패 후 재실행. 별도 합성 데이터로 실행하며 실제 고객 정보를 테스트 파일에 넣지 않는다.

## 8. 역할 분담과 완료의 의미

- 메인 에이전트: 요구사항과 상세 설계, 단계별 검토, 최종 통합.
- 구현: 깊이 1의 서브 에이전트, 기본 `gpt-5.6-sol / medium`. 복잡한 문제는 `gpt-6-astra / xhigh` 사용. 추가 하위 에이전트 위임 없음.
- 구현 에이전트의 보고는 변경 파일, 검증 결과, 남은 문제 중심으로 제한한다.

1차 완료는 로컬에서 확인된 과거 문의를 가져와 조회하고, 실행 환경이 켜져 있으며 인증이 유효한 동안 시간당 신규 문의를 중복 없이 반영하고 WARP 고객관리로 전달하는 상태다. 실패와 데이터의 마지막 갱신 시점도 사용자가 알 수 있어야 한다.

상시 서버 이전은 로컬 검증 후의 별도 단계다. 이번 계획서 작성으로 구현·실제 데이터 수집·배포가 완료된 것은 아니다.
