# Marketing cloud release wiring

This implements the bounded cloud boundary of M3 in [the existing deployment plan](zero-downtime-deployment-plan.md), alongside the [dedicated-server plan](dedicated-server-plan.md). It is source code and declarations, **not an AWS deployment or operational acceptance record**. No account, instance, domain, secret, initial journal, backup or proxy is assumed to exist. No AWS resources have been created or queried for this work.

The coordinator uses Python stdlib and Docker CLI directly, replacing the plan's proposed Compose layer. There is one configuration source: `/opt/evn-marketing-runtime/config.json`. Controller changes and its config/state format are maintained with `deploy/controller.py`; there is no second Compose configuration. The controller uses `state/release.json`, the named volume `evn-marketing-data`, network `evn-marketing`, and containers `evn-marketing-web-blue`, `evn-marketing-web-green`, `evn-marketing-worker` and `evn-marketing-proxy`.

## Boundary and inputs

`.github/workflows/release.yml` accepts only `workflow_dispatch` on `EVNSolution/EVN-MARKETING` main. Required input `source_sha` must be the full lowercase 40-character SHA, equal to the dispatched workflow SHA, checkout HEAD and current remote main. A second check immediately before dispatch rejects main advancement during approval/build. Select `release` or `rollback`; there is no remote recovery, expiry, shell, URL, path, arbitrary image or arbitrary rollback target input.

All steps run in the `production` environment, with a shared release/rollback concurrency group and `cancel-in-progress: false`. Third-party actions are pinned to full commits. Checkout cannot persist credentials. OIDC provides a short-lived Marketing-only role; runtime secrets never enter GitHub Actions. The actual GitHub protection settings must be configured before activation; declaring the environment in YAML does not create its approval rules.

| Production environment variable | Value supplied during reviewed activation |
| --- | --- |
| `MARKETING_AWS_ACCOUNT_ID` | The real 12-digit Marketing AWS account ID |
| `MARKETING_INSTANCE_ID` | The one existing dedicated Marketing EC2 instance ID |
| `MARKETING_SSM_DOCUMENT_VERSION` | Reviewed positive integer version of `EVN-Marketing-Release`, never `$LATEST`/`$DEFAULT` |
| `MARKETING_SSM_DOCUMENT_SHA256` | AWS-returned SHA-256 of that exact reviewed document version |

These are identifiers, not credentials. Missing/invalid values fail before AWS credentials are requested. No sample real account or ARN is supplied. Region is fixed to `ap-northeast-2`; repository is fixed to `evn-marketing`; role is `EVN-Marketing-Release`.

Resolve existing name conflicts through administrator review, not replacement/deletion. The GitHub OIDC provider must already exist with audience `sts.amazonaws.com`. Reuse of the provider does not grant access to WARP roles.

Trust uses `StringEquals`, with no wildcard repo/environment. The environment-form subject does not also encode the branch, so the main-only environment rule is essential. [GitHub OIDC requirements](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)

Install exactly `deploy/controller.py` and `deploy/nginx-config.mjs` under `/opt/evn-marketing-runtime/deploy/`; all ancestors, code and config must be root-owned, non-symlink, and not group/other writable. 6. Install Python 3, Docker Engine, AWS CLI, current SSM Agent **3.3.2746.0 or newer**, and the Amazon ECR credential helper. Configure `/root/.docker/config.json` (root-owned, helper mapping only) with Docker `credHelpers` for the exact account's Seoul ECR registry using `ecr-login`, with instance-profile credentials and `AWS_ECR_DISABLE_CACHE=true`; no `docker login` auth entry or credential cache. Provision `/run/evn-marketing-ecr` as a root-only directory at boot for helper logs; token caching is disabled. Ensure helper/CLI executables are administrator-owned. An older SSM agent lacking parameter environment interpolation fails closed; no raw interpolation fallback is provided. [SSM parameter interpolation](https://docs.aws.amazon.com/systems-manager/latest/userguide/documents-schemas-features.html), [ECR credential helper](https://github.com/awslabs/amazon-ecr-credential-helper)

Both current and candidate images must contain `/app/worker-activation.version` with version `1`; a pre-marker image cannot be the origin of an automated release. First install a compatible current version through the separate bootstrap procedure. The controller's read-only snapshot check is not a backup creator or a substitute for restore evidence. Bootstrap remains a separate implementation/approval gate.
8. Create only the four Marketing SecureStrings below through the approved secret channel, encrypted under the supplied Marketing key. Populate the controller's `parameters` mapping with these exact names, never values. No wildcard path listing, WARP parameter reads or CI secret access is granted. The host KMS permission is limited to the supplied key, SSM in Seoul, and those four parameter encryption contexts. The release role can upload only to Marketing ECR and send only the custom Marketing document to the configured instance. It cannot change IAM/documents/infrastructure, read SecureStrings, create sessions or run `AWS-RunShellScript`. The custom document internally uses the shell plugin with a fixed program, not user-supplied shell commands.

AWS requires wildcard resources for ECR token retrieval and some SSM agent/status and EC2 describe APIs. These are enumerated actions, region-limited where used; `GetCommandInvocation` cannot be scoped to one command ARN, and `DescribeSnapshots` cannot be narrowed to one snapshot ARN. Status read permission can read other known command IDs in that account/region; it does not grant execution on other instances. No broader AWS managed host policy is attached. The minimal agent policy uses `ssmmessages`; connectivity and receipt of the custom command still require Linux/SSM validation. ## Release and rollback behavior

Release runs source checks and `npm audit --omit=dev --audit-level=high`. It builds one `linux/amd64` image for the exact SHA when the immutable SHA tag is absent, or reuses the existing image when present. Permission/network failures are not interpreted as absence. The image carries source/revision/run labels. CI uses the runner's ECR credential helper with OIDC credentials and disabled token cache; temporary Docker config contains only the helper mapping. No passwords are put in argv, logs or artifacts.

Immediately before SSM dispatch, the source tag is resolved again and must match the approved digest. The ECR gate requires `COMPLETE`, the same image digest, scan completion and vulnerability-source timestamps within 24 hours, and no HIGH, CRITICAL or UNDEFINED findings. Pending scans have a ten-minute bound; missing, failed, unsupported, stale or enhanced `ACTIVE` results fail closed. For an old immutable image, a separately reviewed rescan may be needed before retry. Basic ECR scanning covers OS packages; npm audit separately checks production lockfile dependencies. Neither is a full exploitability or image-provenance assessment. [ECR basic scanning](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-scanning-basic.html)

The helper hashes a manifest of `SHA256(file) + two spaces + relative path + newline`, in this fixed order: `deploy/controller.py`, `deploy/nginx-config.mjs`. It then SHA-256 hashes that manifest. The SSM document recomputes this from administrator-owned installed files **before any controller code executes**. Config/state are administrator-controlled mutable operational records and are not included in the source bundle hash. System units are separately administrator-installed and not release payloads. Any future runtime dependency must be added to both fixed bundle lists and their test before activation.

SSM parameters are environment-interpolated and independently validated as an allowlisted action, full source SHA, `sha256:` plus 64 lowercase hex (or `previous` for rollback), and a 64-hex bundle checksum. The document has a fixed config location, a sanitized process environment, no shell substitution of inputs, and no remote code download. It runs only:

```text
python3 /opt/evn-marketing-runtime/deploy/controller.py release --revision SHA --digest sha256:HEX
python3 /opt/evn-marketing-runtime/deploy/controller.py rollback
```

The implementation uses `/usr/bin/python3 -I` for isolated Python execution. Rollback's `source_sha` still identifies the **current main controller bundle**, not the previous application SHA. Its target comes exclusively from stored previous-release state and retains the latest DB/uploads/receipts. An unavailable previous release or incompatible current schema blocks rollback. The controller keeps its host lock across observation and drain; workflow concurrency does not replace that lock.

SSM pins both numeric document version and the AWS-issued document hash. Its execution timeout is 3,600 seconds, with a 120-second delivery-start bound. CI allows 80 minutes for scan/dispatch/confirmation and 135 minutes for the job, covering the controller's 1,800-second observation plus drain. Release-role credentials last two hours after acquisition. No workflow-wide automatic retry or cancellation of an uncertain SSM command is implemented. [SSM version/hash/timeout semantics](https://docs.aws.amazon.com/cli/latest/reference/ssm/send-command.html)

The run summary records only source SHA, digest/`previous`, controller bundle hash and SSM command ID. Controller stdout/stderr are suppressed at this boundary; CI retrieves only SSM status/response code. Success requires terminal SSM `Success` and response code zero, not merely a successful `SendCommand` response. If dispatch response is lost, polling fails, the workflow is cancelled or timeout occurs, **do not redispatch blindly**: an administrator must find the corresponding command/run and inspect the host's journal/lock/actual containers. A cancelled GitHub run does not prove that SSM stopped. Recovery/expiry remain host systemd/administrator operations, never extra workflow actions.

## Local validation and remaining evidence

```text
python3 tests/cloud-release.test.py
```

The stdlib assertions exercise source/action/config validation, scan failures/staleness, exact target/document request construction, the actual inline SSM verifier with synthetic files and mocked execution, checksum/permission/symlink rejection, rollback argument isolation, and declared IAM boundaries. Workflow YAML is additionally parsed with the already-installed `js-yaml`, and its embedded shell is syntax-checked without execution.

This cloud-wiring work does not run CloudFormation `ValidateTemplate`, IAM simulation, ECR push/scan, OIDC assumption, SSM, a Docker daemon, systemd or a production command. AWS CLI is installed locally; Docker, `cfn-lint`, `actionlint` and `systemd-analyze` were not present during initial inspection. The parent implementation supplies `tests/deploy-controller-lab.py` for synthetic Docker/Nginx/TLS/SQLite transitions with accelerated observation; its execution/evidence is reported separately. Passing these local checks proves neither deployed policy behavior nor no-downtime release. Actual AWS bootstrap, normal-duration observation and boot/operational evidence remain gates; **full Z01–Z09 acceptance and M5 operational transition are not claimed**. Preserve the existing plan's browser, request continuity, worker ownership, backup/restore and data-preservation gates. Recovery may accept an expired lease only after process absence is established; it does not automatically clear lease records in the DB, and root owns the journal/backup evidence.
