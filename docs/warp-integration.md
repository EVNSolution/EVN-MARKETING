## 신원미상 이름 보정 후속 작업

이름 자동 생성 후속 작업(2026-09-17): 사용자가 연락처만 있는 고객에게 WARP의 `이름을 모를 때 · 신원미상` 규칙을 적용하도록 요청했다. 이번 연동으로 전달된 고객과 대조해 운영 화면에서 이름이 공란인 7명을 확인했고, 해당 버튼과 저장 기능으로 보정했다. 7명 모두 새로고침 후 이름 유지 및 이름 외 입력·선택·메모 항목 불변을 확인했다. 확인 시점에 연락처가 있으면서 이름이 빈 B2C 고객은 0명이었다. 보류 3건은 기존 고객 선택이나 병합 없이 그대로 유지했다.

앞으로의 자동 생성은 WARP 수신기의 신규 고객 생성 시 기존 `unknownCustomerName` 함수를 재사용하도록 [후속 PR #50](https://github.com/EVNSolution/EVN-WARP/pull/50)에 준비했다. 수신기 12개 테스트, 양쪽 계약 검사, 린트·타입 검사, 실제 발신기와 변경 수신기의 합성 연결 검사가 통과했다. 원본 성함 공란은 로컬 문의와 CRM 활동에 보존하며, 이미 존재하는 고객 프로필은 자동으로 덮어쓰지 않는다. 이 후속 변경은 PR #49 배포와 구분해 운영 담당자의 검토·배포를 받아야 한다. 현재 7명 보정 완료를 향후 자동 생성 코드의 운영 배포 완료로 해석하지 않는다.

2026-09-29 사용자 후속 요청: [Marketing PR #21](https://github.com/EVNSolution/EVN-MARKETING/pull/21)에서 신규 수집 시 이름이 없으면 같은 신원미상 규칙으로 저장하고, 기존 공란 문의도 조회·전송 시 이름을 채운다. 이후 발신된 문의의 CRM 이력에는 이 이름이 포함된다. 위 9월 17일의 공란 보존 정책을 변경하며, 기존 WARP 고객 프로필과 완료된 전송 기록은 변경하지 않는다. 원본 서비스의 성함은 수정하지 않는다. 아직 운영 반영 전이며 자동 등록 설정과 기존 배포·검증 절차는 유지한다.

## 활성화 전 확인 기록

- 운영 `/api/readyz`는 HTTP 200이며 revision은 `96e20be7d25261342a0dc1e15b553d0460bbe385`다. 로컬 WARP main도 같은 커밋이다.
- 키 없는 빈 요청은 HTTP 401 `unauthorized`였다. 현재 Mac에서 수신 경로와 인증 경계에 접근된다는 확인이며, 올바른 키 인증이나 실제 등록의 증거는 아니다.
- 양쪽 `docs/integrations/WARP_MARKETING_INQUIRIES.json`과 `.md`는 검토된 커밋과 동일하다. 계약 상태는 `source-reviewed-activation-pending`이다.
- 최초 확인 시 로컬 문의 401건, WARP 전달 완료 0건, 오류 0건이었다. 미전송 문의의 UUID, 연락처 자릿수, 이름·상태 길이를 집계 검사했고 형식 위반은 없었다. 같은 날 로컬 앱과 수집기를 다시 실행한 뒤 자동 로그인·신규 수집이 성공해 408건이 됐다. WARP 자동 전송은 계속 비활성이다.
- 담당자 답변에 따르면 운영 전용 키는 설정됐다. 로컬에는 아직 없으므로 담당자에게 별도 보안 경로로 전달받아야 한다. 운영 SSM 전체를 내려받거나 기존 BUILDUP 키를 대신 사용하지 않는다.

이 상태와 건수는 위 날짜의 확인 기록이다. 실제 전송 완료를 뜻하지 않는다.

## 처리 방식

1. 원본 문의는 각각 보존한다. 정기 수집은 마지막 성공 수집 경계까지의 신규 문의만 추가한다.
2. `WARP_MARKETING_API_KEY`와 `WARP_DELIVERY_ENABLED=true`가 함께 설정돼야 자동 전송한다. 키만 설정하면 비활성 상태를 유지한다.
3. `POST https://warp.cleversystem.ai/api/external/marketing-inquiries`로 한 번에 최대 50건을 순차 전송하고 다음 순회에서 나머지를 이어간다. 기존 문자열 9개와 `rejectExistingCustomer: true`를 보낸다. 이 guard를 지원하는 [WARP PR #51](https://github.com/EVNSolution/EVN-WARP/pull/51)은 승인·배포 전이다.
4. 기본 연락처의 숫자가 완전히 일치하는 기존 고객 한 명이면 기존 프로필을 유지하고 새 문의 이력만 추가한다. 일치 고객이 없으면 B2C 잠재고객을 만든다. 회사 대표번호·추가 연락처로 매칭을 확대하지 않는다.
5. 여러 고객의 연락처가 같으면 `warp_customer_conflict`로 보류하고 자동 재시도하지 않는다. 운영자가 중복 고객을 확인한 뒤 재개 여부를 결정해야 한다.
6. 원본 UUID를 소문자로 정규화해 결정적인 활동 ID를 검증한다. 성공 응답의 고객·활동 ID와 `created`/`duplicate` 조합이 유효해야 완료 처리한다. `created`는 문의 활동 생성 여부이며 신규 고객 생성 여부가 아니다.
7. 날짜·시간 문자열은 보존하고 CRM 날짜는 한국 시간으로 해석한다. 고객 또는 활동 삭제 시 해당 중복 방지 기록도 삭제되므로 완료 문의의 임의 재전송 기능은 제공하지 않는다.

원본 다섯 필드는 CRM 활동 내용에서 확인한다. 화면의 대기 건수에는 오류 건수도 포함된다. 인증·접속·응답 규격 오류는 전체 전송을 1시간 멈춘다. 그 외 개별 실패는 1시간 후 다시 시도하지만 연락처 충돌은 계속 보류한다. 고객 정보, 실제 키, 응답 본문은 로그로 남기지 않는다.

WARP #51이 승인·배포된 뒤에는 guarded payload가 더 이상 400 `bad_payload`로 거부되지 않는지 먼저 확인한다. worker를 멈추고 새 백업을 확보한 상태에서 `warpError = 'warp_registration_guard_unavailable'`인 행만 집계한 뒤, 그 행의 `warpError`와 `warpAttemptedAt`만 `null`로 되돌려 재개한다. receipt ID와 전달 시각, `warp_existing_customer`, `warp_receipt_unverified`, 다른 오류는 수정하지 않는다. 변경 건수를 사전 집계와 대조한 뒤 pilot과 CRM 확인을 거쳐 자동 전송을 다시 켠다.

## 활성화 순서

개발 checkout에서는 아래 `npm run warp:delivery -- check|pilot` 명령을 사용합니다. 최종 컨테이너의 `/app`에서는 같은 기능을 `node warp-delivery.mjs check` 또는 `node warp-delivery.mjs pilot`으로 실행합니다. 이미지에는 점검용 JS 번들을 포함하며 `tsx`나 Prisma CLI를 설치하지 않습니다. 실행 환경에는 승인된 전용 키를 주입하고, `pilot`에는 이전·검증된 DB를 연결해야 합니다. 키가 없거나 형식이 맞지 않으면 두 모드 모두 DB를 열거나 worker lease를 잡기 전에 `warp_key_required`로 실패합니다.

1. 전용 키를 승인된 보안 경로로 전달받아 실행 프로세스의 환경변수로 주입한다. 키는 채팅, 명령 인자, `.env`, Git, 문서, 로그, 브라우저에 넣지 않는다. 자동 전송은 계속 비활성으로 둔다.
2. `npm run warp:delivery -- check`를 실행한다. 인증된 빈 요청이 HTTP 400 `bad_payload`를 반환하면 `ok`다. CRM에는 쓰지 않는다.
3. 실행 중인 수집 worker를 정상 종료한 뒤 `npm run warp:delivery -- pilot`을 실행한다. 같은 worker lease로 보호하며, 대기 문의 1건과 동일 문의의 재전송만 검사한다. 첫 응답은 `created=true, duplicate=false`, 재전송은 `created=false, duplicate=true`여야 하고 고객·활동 ID가 같아야 한다.
4. 첫 전송에서 `created: true`를 확인하고 같은 실행의 replay가 일치하면 정상 완료한다. 최초 응답 증거 없이 replay receipt만 확인한 경우는 `ok_recovered_receipt_unverified`와 `등록 확인 필요`로 남긴다. 재시도 대기 시간과 무관하게 같은 가장 오래된 미완료 문의를 선택하며 연락처 중복과 guard 보류는 제외한다.
5. WARP 고객관리에서 신규 고객 또는 기존 고객 프로필 보존과 문의 이력의 날짜·시간·상태를 직접 확인한다. CLI 성공만으로 이 확인을 대신하지 않는다.
6. 위 확인 후에만 `WARP_DELIVERY_ENABLED=true`로 worker를 재시작해 나머지를 순차 처리한다. 로컬 화면에도 상태를 반영하려면 앱 프로세스에 같은 활성화 설정이 필요하다.
7. Issue #48에 발신기 커밋, 합성 검사, 인증 검사, 최초·재전송 결과, CRM 확인, 완료·대기·오류 집계를 남긴다. 키나 고객 식별정보는 포함하지 않는다.

401은 키 확인, 503 `not_configured`는 담당자의 설정 확인, 503 `temporarily_unavailable`은 지연 후 동일 UUID 재시도 대상이다. 409 `ambiguous_phone`은 운영자 확인이 필요하다. 운영 DB 직접 쓰기나 별도 배포로 우회하지 않는다.

## 로컬 검증

- 합성 검사: 자동 전송 비활성 시 HTTP 호출 없음, 인증된 빈 요청, 한 건 파일럿과 재전송, 첫 응답 유실 뒤 같은 문의 복구, UUID 대소문자, 잘못된 수신 확인, 503 재시도, 409 보류, worker lease.
- 배포된 `96e20be`의 수신 코드를 합성 DB에 연결해 발신기와의 호환성 및 고객·활동 중복 방지를 확인했다. 운영 DB에는 접근하지 않았다.
- 수집 회귀 검사, 타입 검사, 변경 파일 ESLint, 계약 검사가 통과했다. 검토된 양쪽 계약 파일의 바이트 일치와 변경 파일의 기존 로컬 비밀값 혼입 없음도 확인했다.
- 문의 수집은 2026-09-17 12:24 KST에 성공했고 다음 수집은 13:24 KST로 예약됐다. 실행 시 앱과 worker에 `WARP_DELIVERY_ENABLED=false`를 명시했다.

## 완료 기준과 제한

실제 문의 1건의 최초·재전송과 CRM 확인을 마친 후 미전송 문의를 순차 처리한다. 다중 고객 연락처 충돌은 자동 완료로 처리하지 않으며 담당자가 확인해야 한다.

로컬 앱과 수집기는 Mac이 켜져 있고 프로세스가 실행 중일 때 동작한다. 키는 실행 프로세스의 환경변수에만 주입했으며 `.env`, 명령 인자, Git, 문서, 로그에 저장하지 않았다. Mac 재시작이나 앱·worker 종료 후에는 키를 안전하게 다시 주입해야 한다. 신규 전용 수집은 과거 수정·소급 삽입을 대조하지 않는다. 수신기는 기본 연락처를 스캔하므로 실제 CRM 규모에서 느려지면 정규화 연락처 열과 인덱스를 검토한다.

## 중복 문의의 WARP 이름 보완

- 관리자 → 문의 내역 → 중복 문의 검토 → **WARP 이름 보완**에서 같은 휴대폰 번호의 실명 문의를 선택한다. 기존 등록 완료 문의도 이름의 근거로 사용할 수 있다. 서로 다른 실명이 있으면 자동 선택하지 않는다.
- **WARP 이름 확인**은 기존 수집기의 조회 대기열을 사용한다. 확인된 현재 이름·제안 이름·휴대폰 번호를 비교하고 동일 고객 확인란을 선택한 뒤 **확인한 이름으로 보완**을 누른다. 수집 연결이 없으면 요청하지 않는다.
- WARP의 기본 휴대폰 번호에 유일하게 일치하는 고객이 있고 이름이 공란·미상·해당 번호뿐일 때만 변경한다. 실명이 이미 있거나 고객이 여러 명이면 안내하고 변경하지 않는다. 리드만 있는 경우에도 고객을 새로 만들지 않는다.
- 저장 직전 원격 고객과 로컬 근거 문의를 다시 확인한다. WARP 이름과 변경 활동 기록만 함께 저장하며 문의 원문, 기존 등록 영수증, 중복 상태, DB 유입 집계 및 리드는 그대로 둔다.
- 웹에는 WARP 키를 주입하지 않는다. 기존 키 소유 수집기만 전용 API를 호출하며 서명된 확인 토큰은 브라우저로 보내지 않는다. 짧은 검토 대기열은 비공개 공유 저장소 `_reports/warp-customer-name/pending.json`에 저장하며 기존 DB 쓰기 잠금과 수집기 임대로 직렬화한다. 20분이 지난 검토 자료는 다음 접근/수집 주기에 제거한다. 영구 변경 이력은 WARP 고객 활동에 남는다.
- 통신 결과가 불명확하면 동일 확인 요청을 최대 3회 재시도한다. 처리 결과를 확인하지 못한 경우 성공으로 표시하지 않고 WARP 재조회 안내를 표시한다. WARP는 같은 확인 요청의 보존된 변경 이력과 현재 고객이 일치할 때만 재처리 완료를 반환한다.
- 배포 순서는 WARP 수신 기능 → Marketing 화면·수집기다. 스키마, IAM, 키 배포 범위를 변경하지 않는다. 운영 검증에서는 실고객의 이름을 변경하지 않고 조회와 화면만 확인한다.
