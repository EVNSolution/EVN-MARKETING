# 외부 대시보드 날짜별 보관

`/external-dashboard`에서 성과 시작일·종료일을 고르고 **기간 조회**를 누릅니다. **시작일 하루 조회**는 시작일 하루만, **오늘**은 한국 시간의 오늘을 조회합니다. 한 번에 최대 366일을 조회하며 **기존 집계 보기**는 최근 원본 집계 기간으로 돌아갑니다. 날짜 범위와 별개로 **원본 보관본 수집일**에서 수집일별 마지막 성공 원본의 네트워크·키워드를 선택합니다.

## 실제 원본의 범위

- 성과 날짜가 붙은 `monthlyViews`(원본 `aggregationDates` 포함 일자), `monthlyAdViews`만 일별 관측값입니다. 방문자는 일별 방문자 합계이며 기간 순방문자가 아닙니다.
- `monthlyInflows`, `monthlyKeywords`에는 날짜가 없으므로 기간을 나누거나 전날과 차감하지 않습니다. 각 카드에 원본 실제 집계 기간과 보관본 수집시각을 표시합니다. 날짜 필터를 바꿔도 이 순위를 선택일의 성과로 부르지 않습니다.
- 2026-10-09 컨트롤타워의 원본 화면 확인에서 집계는 9/11~10/8이고 날짜 입력/선택 기능은 관찰되지 않았습니다. 숨겨진 `today*` 필드나 추측한 query parameter는 사용하지 않습니다. 오늘의 날짜별 행이 없으면 **원본 공개 대기**이며, 이후 기존 수집 일정에서 그 날짜가 실제 제공되면 보관합니다.
- 원본에 없는 날짜·매체를 0으로 만들지 않습니다. 실제 0은 그대로 표시합니다. 누락된 기간은 수집된 날짜의 부분합임을 표시하고 일별 표에서 미수집을 구별합니다. 매체 값은 각각 마지막 관측 시각을 표시하므로 누락 매체의 이전 값이 섞인 것도 확인할 수 있습니다.

## 저장과 복구

영구 `UPLOADS_DIR/_reports/external-dashboard/` 아래에 다음을 둡니다. 외부 다운로드 URL을 만들지 않으며 기존 업로드 인증/경로 정책에서 차단됩니다.

- `current.json`: 기존 format 1을 그대로 유지합니다. 최근 수집 상태, 실패 시 마지막 성공 데이터 유지. 구버전 reader/worker로 rollback할 수 있습니다.
- `history.json`: format 1의 날짜별 관측값과 수집시각, 범위가 검증된 `latest` 성공 원본. 동일 날짜/매체의 새 관측값은 교체하며 누락은 지우지 않습니다. 32 MiB, 50,000일의 방어 한도를 넘으면 저장을 거절하며 오래된 데이터를 자동 삭제하지 않습니다.
- `snapshots/YYYY-MM-DD.json`: **수집일(KST)** 별 마지막 성공 원본, 기존 record format 1. 날짜는 성과일이 아닙니다. 각 파일은 최대 5 MiB입니다.
- `preserved-20261009.json`: 컨트롤타워가 별도로 보존한 기존 format 1 파일이 있으면 정확한 고정 이름으로만 읽어 초기 이관에 포함합니다. 없어도 `current.json`으로 시작합니다. 원본 파일은 변경·삭제하지 않습니다.

인증된 조회는 파일을 쓰거나 수집 작업을 추가하지 않습니다. 초기 조회에는 기존 current/보존본을 메모리에서 합쳐 즉시 보여줍니다. 실제 영구 이관은 기존 worker lease와 SQLite writer transaction 안에서, current 교체 전에 이루어집니다. 파일마다 scope/format/크기/값을 검증하고 symlink·hardlink를 거절합니다.

한 성공 저장의 순서는 이전 `history.latest`의 수집일 보관 완료 → 기존 보존본/current 이관 → 새 history 원자적 교체 → 새 수집일 보관본 교체 → current 교체입니다. 각 publish 직전에 lease를 재확인하며 임시 파일 fsync, rename, Linux 디렉터리 fsync를 사용합니다. 파일 사이를 하나의 원자적 transaction이라고 가정하지 않습니다. history는 성공 원본 전체를 함께 담는 durable journal이므로 보관본/current 쓰기 전 중단되어도 조회에서 새 정상 데이터를 읽을 수 있고 다음 fenced 저장에서 누락된 수집일 보관본을 마무리합니다. 완성되지 않은 UUID 임시 파일은 읽지 않습니다.

JSON 손상, link, 범위 불일치, 크기 초과는 실패로 처리합니다. 손상 파일을 빈 정상 데이터로 덮어쓰거나 과거 값을 0으로 만들지 않습니다. 조회 오류 시 UI는 이미 표시한 마지막 결과를 유지합니다. 운영 복구는 손상 파일을 먼저 보존하고 검증된 백업을 사용하는 기존 절차를 따릅니다.

DB schema, dependency, 운영 환경 변수, 수집 일정, 문의/CRM/landing 쓰기 흐름은 추가·변경하지 않았습니다. 새 파일은 기존 uploads 전체 재귀 inventory/hash/백업/복원에 포함됩니다. 구버전은 추가 파일을 건드리지 않으며 다시 업그레이드하면 rollback 중 마지막 current도 이관합니다. 구버전으로 오래 운영해 원본 rolling 창에서 이미 사라진 미보관 일자는 복원할 수 없습니다.

## 검증

`npm run test:external-dashboard`는 rolling 보존, format1/보존본 bootstrap, 정정·누락·실패·lease, journal 중단 복구, 동시 조회, 날짜/KST, 순위 범위 분리와 파일 방어를 검사합니다. 기존 container browser 검사에 1440/390/320px 날짜 조회·보관본 선택·인증·private no-store·원본/CRM 무변경 검증이 포함됩니다. `npm run test:backup`은 history/수집일 보관본/이관 원본을 모두 복원하고 각 파일 손상 탐지를 확인합니다.
