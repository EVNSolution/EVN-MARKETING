# 배포 인수 검사: 실제 시간과 중단 복구

PR #9의 컨트롤러를 기존 격리 Linux CI에서 검사합니다. 운영 AWS 자원, 원본 로그인, 실제 고객 DB와 WARP 전송을 사용하지 않습니다. 앱과 합성 수집기는 외부 통신 없는 Docker internal network에 있고, 합성 HTTPS 앞단은 시험 호스트의 loopback에만 연결합니다.

## 두 검사 경로

일반 `PR checks`는 기본 lab을 실행합니다. 관측창만 가속하여 A→B→A, 수집기 준비 실패 후 복귀, 진행 중 요청의 drain, 배포 프로세스 중단과 저장된 journal 복구를 검사합니다. 실제 프로세스의 시작/종료 대기는 가속하지 않습니다. 기존 구버전 브라우저·동시 업로드 검사도 유지합니다.

별도 `Release acceptance (30 minutes)`는 검토 대상 PR에 `release-acceptance` label을 추가하면 실행합니다. 일반 검사 통과 후 같은 소스에 대해 실행하고, 이후 코드가 바뀌면 label을 제거/재추가하여 다시 검증합니다. 자동 재전송이나 주기 실행은 없습니다. fork PR은 실행 대상에서 제외합니다. 이 workflow에는 AWS 역할, 운영 environment, 실제 비밀값이 없습니다.

```text
python3 tests/deploy-controller-lab.py --real-time --report REPORT_PATH
```

실제 시간 경로는 동일한 컨트롤러의 1,800초 관측값을 줄이지 않고 **A→B 한 번**을 실행합니다. `time.time`/`time.monotonic`과 실제 대기를 사용하며 전환 시작부터 commit까지 최소 1,800초인지를 별도로 확인합니다. 이 실행이 가속된 rollback·중단 복구 검사를 대체하지 않습니다. 두 workflow의 정확한 소스와 성공 결과를 함께 확인합니다.

## 확인하는 내용

- 공개 HTTPS readiness를 전환 전부터 지속 조회합니다. HTTP/연결 오류 0, 최소 1,800개 probe, probe 간 최대 공백 5초 미만을 요구하고 응답 지연 p95를 기록합니다. 이는 합성 시험 기준이며 운영 SLO나 서버 사양 측정 결과가 아닙니다.
- 두 API 클라이언트가 고객 조회·저장·파일 업로드·다운로드를 동시에 반복합니다. Nginx 내부 경로에 합성 인증 세션을 메모리로만 전달하며, 실패를 재시도해 숨기지 않습니다. 각 성공 응답을 즉시 HTTP·DB·파일과 대조합니다. 문서를 명시적으로 교체하므로 이전 파일의 의도된 삭제와 데이터 유실을 구분합니다. 실제 로그인 UI는 기존 브라우저 검사가 담당합니다.
- 이전 버전으로 전송 중인 multipart 요청을 일부러 열어 두고 매핑을 만료시킵니다. 구 Nginx worker가 요청 완료 전까지 유지되는 것을 확인한 다음 나머지 body를 보냅니다. 이전 slot에서 HTTP 200을 받고 파일을 읽을 수 있어야 drain 성공입니다. 이는 실제 진행 요청 검사이며 180초 drain 한도 전체의 부하 시험은 아닙니다.
- 복구 helper는 실제 별도 프로세스의 강제 종료, 호스트 잠금 경쟁, 저장된 journal 재읽기, 컨테이너 중단 후 재시작을 사용합니다. 정상 종료 경로를 호출한 결과만으로 crash 복구를 주장하지 않습니다. 확인한 상세 시나리오는 결과 JSON의 recovery 항목으로 남깁니다.

실제 시간 성공 시 `marketing-acceptance-<source SHA>` artifact에 집계 JSON 하나만 저장합니다(7일 보관). 소스 SHA, 합성 이미지 digest, 경과 시간, 요청 수/오류/지연, drain 결과를 담고 세션·비밀값·고객 내용·DB·전체 journal은 업로드하지 않습니다. 실패나 취소는 성공 보고서를 만들지 않습니다.

## 남는 운영 경계

컨테이너 정지/재시작은 **OS 재부팅이 아닙니다**. CI 프로세스 사망은 실제 AWS SSM 연결 중단이 아닙니다. 실제 host boot ordering, systemd 자동 복구, SSM 실행 중단·명령 결과 유실, 실제 원본 서비스의 장기 로그인, 모든 Z01–Z09 조합은 운영 준비 환경에서 별도 확인해야 합니다. 두 fixture는 현재 소스에 합성 revision을 부여하므로 서로 다른 소스 버전의 호환성 증거는 기존 브라우저 검사와 구분합니다. 이후 M4에서 일관된 백업/복원·receipt 대조와 사양 측정을 진행합니다.
