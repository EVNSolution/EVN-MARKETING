## 채택한 방향

- 웹과 worker는 동일 release 이미지에서 실행하고, 일반 배포에서는 old/new 웹 두 버전과 worker 한 개가 일시 공존합니다. 배포 완료 시 웹/worker digest가 일치해야 합니다.
- 일반 앱 배포는 기존 웹을 유지한 채 후보를 검증하고 프록시를 전환합니다. 프록시·worker 검증 실패 시 최신 DB를 유지하며 이전 호환 버전으로 되돌립니다.
- 초기 Mac 이전, 비호환 schema 변경, 일관된 전체 DB+업로드 백업은 필요한 writer 정지 범위를 명시한 별도 작업입니다. 단일 서버의 호스트 장애까지 고가용성으로 포장하지 않습니다.
- 실제 DB와 업로드는 이미지/소스에 넣지 않고 영속 볼륨에 보관합니다. seed나 `prisma db push`를 컨테이너 시작에 실행하지 않습니다.
- 운영 비밀값은 Marketing 전용 경로에서 역할별로 주입합니다. WARP 전체 SSM 환경값, 기존 BUILDUP 키, WARP 배포 역할을 복사하지 않습니다.
- 로컬 수집기와 서버 수집기의 별개 DB lease는 서로를 막지 못합니다. 최종 전환에서는 로컬 프로세스·자동 실행·자격증명 자동 주입을 중지하고 서버 하나만 운영합니다.

### 서버 준비 상태 확인

후속 M2 변경의 `GET /api/readyz`는 준비 완료 시 HTTP 200과 `ok`, `revision`, `imageDigest`만 반환합니다. 실패 시 HTTP 503과 `{"ok":false}`만 반환하며 항상 `no-store`입니다. 이 경로만 세션 없이 점검할 수 있고 고객·문의 API의 기존 인증은 유지합니다. 고객 수, 저장 경로, 오류 원문, 원본/WARP 인증값은 공개하지 않습니다.

준비 조건은 다음과 같습니다.

- `MARKETING_REVISION`은 40자리 소스 SHA, `MARKETING_IMAGE_DIGEST`는 `sha256:` 뒤 64자리 hex입니다. 주입된 식별값이며 실제 실행 이미지 증명은 아닙니다. M3에서 호스트 Image ID/RepoDigest와 승인 산출물을 별도로 대조해야 합니다.
- `DATABASE_URL=file:/data/marketing.db`처럼 기존 파일의 절대 경로를 사용하고 `UPLOADS_DIR=/data/uploads`처럼 같은 데이터 디렉터리 아래 업로드 폴더를 연결합니다. 경로·파일 symlink는 허용하지 않습니다.
- 데이터 디렉터리의 `.marketing-volume-id` 내용이 `MARKETING_VOLUME_ID`와 같아야 합니다. 이 값은 비밀값이 아닌 이관·배포 식별자이며, 최초 자료 검증 때 생성·대조하고 이후 같은 볼륨과 함께 보존합니다. 점검 요청은 마커나 빈 DB를 새로 만들지 않습니다.
- 기존 SQLite가 WAL 모드이고 모든 앱 테이블·필수 열·기본키와 문의 중복 방지 등 필수 고유 인덱스가 있어야 합니다. DB 파일 및 기존 WAL/SHM 접근 권한을 확인하고 데이터·업로드 디렉터리에서 임시 파일 생성·동기화·제거를 검사합니다. 업무 데이터와 schema는 변경하지 않습니다. SQLite 자체의 WAL/SHM 보조 파일은 읽기 연결에서도 생성될 수 있습니다.

이 검사는 필수 구조와 저장 공간 접근의 사전 점검입니다. migration checksum/양쪽 버전 호환성은 별도 [DB 호환성 검사](data-compatibility.md)로 확인합니다. 실제 프록시의 active slot, 원본 로그인·worker 상태, 실제 업로드·인증 동작 및 볼륨 백업 검증을 대신하지 않습니다. worker 관측과 배포 컨트롤러는 후속 단계로 구분합니다.

### 진행 중 작업을 보존하는 수집기 종료

SIGTERM/SIGINT를 받으면 다음 수집 작업·페이지·WARP 전송을 시작하지 않습니다. 이미 읽는 페이지는 저장과 실행 기록 정리를 마치고, 이미 보낸 문의는 응답과 receipt 저장을 마친 다음 종료합니다. 수집 중 브라우저를 먼저 닫지 않습니다. 중단된 실행은 `partial`/`interrupted`로 기록하며 기존 `lastSuccessfulAt`과 `nextRunAt`을 유지합니다. 작업 선점 도중 중단되면 트랜잭션을 되돌리거나, 이미 선점된 실행을 정리하여 잠금만 남기지 않도록 합니다.

저장·소유권 확인·정리 실패는 성공 종료로 처리하지 않습니다. 기존 로그인 재시도·대기 중에도 종료 신호를 전달하며, 중단 후 소유권을 다시 얻어 작업을 계속하지 않습니다. 개발 Compose의 worker 종료 유예는 210초입니다.

이는 **현재 요청을 마무리하는 협조적 종료**입니다. M3 배포 컨트롤러는 TERM 전달 후 180초를 관측 한도로 사용하고, 정상 종료·프로세스 부재·lease 해제를 모두 확인해야 다음 worker를 시작할 수 있습니다. 시간 초과는 배포 중단/복구 대상으로 처리해야 하며, Docker의 강제 종료를 정상 인계 증거로 사용하지 않습니다. 배포 identity 대조, 원격 commit 뒤 ack 유실 복구와 Z05/Z07 전체 인수 검사는 아직 별도 작업입니다.

### 수집기 상태 확인과 프로세스 경쟁 검사

운영 이미지는 `node worker-health.mjs`를 포함하고 Compose worker의 healthcheck에서 30초마다 실행합니다. 성공은 JSON `ok:true`와 종료 코드 0, 실패는 고정된 사유 코드와 종료 코드 1입니다. DB 파일·schema를 생성하거나 lease를 갱신하지 않고 기존 SQLite를 읽기 전용으로 엽니다. 읽기 연결에서도 SQLite의 WAL/SHM 보조 파일은 생성될 수 있습니다. 원본·WARP 요청이나 비밀값·고객 데이터 출력은 하지 않습니다.

- 새 운영 worker 컨테이너마다 시작 전에 고유 UUID v4 `MARKETING_WORKER_OWNER`를 생성해 그 worker와 점검 프로세스에 동일하게 주입합니다. 예: `node -e "console.log(require('node:crypto').randomUUID())"`. release SHA나 이전 worker의 값을 재사용하지 않습니다. 운영 모드에서 이 값이 없거나 잘못되면 DB 접근 전 실패합니다. 로컬 개발의 미지정 기본값은 기존처럼 임의 UUID입니다.
- 정상 조건은 설정한 owner와 DB owner 일치, heartbeat 나이 180초 미만(미래 5초 초과는 거부), 아직 유효한 lease, `ready`/`running`/`success` 상태입니다. 시작 직후는 `starting`이며 로그인 후 보호된 문의 화면까지 확인한 뒤에만 `ready`가 됩니다. 로그인 대기, 조회 오류, 부분 수집은 비정상으로 표시합니다. 수집 오류가 남은 경우 다음 성공 실행까지 비정상일 수 있습니다.
- 정상 출력은 주입한 `MARKETING_REVISION`/`MARKETING_IMAGE_DIGEST`, heartbeat와 마지막 수집 성공 시각입니다. 마지막 성공이 없으면 null이며, 성공 시각의 지연 알림 기준은 후속 관측 설정에서 정합니다. 주입된 식별값은 이미지의 실제 증명이 아니므로 M3는 컨테이너 Image ID/RepoDigest도 대조해야 합니다.
- 점검 결과는 최근 기록입니다. 갑작스러운 종료·정지·drain을 즉시 증명하지 않으므로 M3는 주 프로세스/컨테이너 실행 상태, 정상 종료, lease 해제를 함께 확인해야 합니다. Compose의 unhealthy 표시만으로 재시작되지는 않습니다. 서로 다른 DB의 로컬/서버 수집기를 함께 막는 장치도 아닙니다.

작업권 획득은 현재 owner가 없거나 만료됐을 때만 가능합니다. 같은 owner 값을 가진 중복 실행도 기존 lease를 획득으로 갱신할 수 없습니다. 유효한 owner의 갱신은 heartbeat만 담당하며, 실행 중 lease를 잃은 worker는 재획득을 시도하지 않고 실패 종료합니다. 교체 컨테이너는 이전 UUID를 재사용하지 않아야 합니다. 같은 컨테이너의 자동 재시작은 이전 주 프로세스가 종료된 뒤 같은 UUID를 유지하며, 강제 종료 뒤에는 기존 lease 만료까지 획득이 거부될 수 있습니다. 그동안 이전 heartbeat가 잠시 보일 수 있어 M3의 주 프로세스/컨테이너 상태 확인이 필수입니다.

`test:worker-health`는 owner·시간·오류 상태·설정 및 DB 미생성을 확인하고, `test:worker-processes`는 실제 자식 프로세스들이 같은 합성 SQLite에서 경쟁하도록 합니다. Linux CI는 이를 실행하고 최종 이미지에서 점검 도구의 성공/실패 및 읽기 전용 동작을 확인합니다. 이 범위는 Z05/Z07의 일부입니다. old/new 웹 동시 업로드·SQLite 부하, 실제 원본 로그인, 원격 commit 후 ack 유실, 배포 인계/복귀 전체를 대신하지 않습니다.

2026-09-22 AWS CLI 재인증 후 서울 리전 자원을 읽기 전용으로 재확인했습니다. EC2 목록에 Marketing 전용 서버가 없으며, 이름에 `marketing`이 포함된 ECR 저장소·SSM 파라미터도 없었습니다. Route 53의 공개 `cleversystem.ai` 영역은 존재하고 `marketing.cleversystem.ai` 레코드는 없었습니다. 다른 리전이나 다른 이름의 자원까지 부재하다고 판단한 것은 아닙니다. 이 확인에서 인프라나 운영 비밀값을 변경하지 않았습니다.

이번 M1 수정은 서버 소유 첨부 경로, 고객별 경로 경계·symlink 차단, 교체/삭제 실패 시 보존 및 변경 충돌 검사, 비공개 캐시, 업로드 크기·형식 검증, 내부 복귀 경로와 수집기 활성화·재로그인 복구를 포함합니다. 합성 파일/DB 기반 보안·수집·전송·계약 검사, 타입 검사와 로컬 빌드를 통과했습니다. lint는 오류 0/기존 경고 4이며, 전체 npm audit의 기존 high 5/critical 0은 남아 있습니다. 이 결과는 실제 원본 로그인이나 운영 배포 검증이 아닙니다.
