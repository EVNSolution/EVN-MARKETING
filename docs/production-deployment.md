# EV&Marketing 서버 이전 준비

작성일: 2026-09-17 (KST). 상태: 서버 실행 구성과 검증 준비. **운영 배포 완료 기록이 아니다.**

## 배포 대상과 현재 확인

- 목적: Mac을 종료해도 원본 신규 문의 수집과 WARP 전달을 1시간 간격으로 계속 실행한다.
- 기존 WARP와 같은 AWS 서버를 우선 대상으로 한다. 2026-09-17 읽기 전용 확인 결과 WARP는 서울 리전, Ubuntu 24.04, x86_64, `t3.micro`(메모리 1GiB, vCPU 2)에서 실행 중이다.
- CloudWatch의 해당 서버 메모리 지표는 확인되지 않았다. CPU 이용률만으로 메모리 여유를 판단하지 않는다. WARP의 활성/이전 컨테이너를 유지한 상태에서 Marketing 웹·Chromium 수집기의 최대 메모리와 디스크 여유를 운영 담당자가 확인해야 한다. 필요 시 서버 증설/분리는 별도 비용·영향 검토 후 결정한다.
- 제안 주소는 `https://marketing.cleversystem.ai`다. 확인 시점 DNS 레코드, Marketing 전용 이미지 저장소와 `/evn-marketing/` SSM 설정은 없었다. 주소는 생성되지 않았다.
- AWS 로그인 갱신과 읽기 전용 조회는 성공했다. 기존 WARP의 `AGENTS.md`상 운영 담당자는 `OziinG`이며 사용자는 앞서 운영 승인 권한을 위임받지 않았다고 밝혔다. AWS 접근 가능 여부를 신규 서비스 설치 승인으로 간주하지 않는다.
- 기존 WARP release workflow는 WARP만 배포한다. 그 workflow 실행만으로 Marketing이 배포되지는 않는다. WARP의 배포 스크립트·DB·SSM 설정을 Marketing 용도로 재사용하거나 임의 변경하지 않는다.

## 코드와 실행 구성

- 소스 검토: 비공개 `EVNSolution/EVN-MARKETING` 저장소. 실제 문의 DB·업로드·인증값은 소스 저장소와 이미지에 포함하지 않는다.
- 동일 이미지에서 웹과 수집기를 별도 프로세스로 실행한다. 웹은 호스트의 loopback 포트 `3100` 제안이며 사용 전 충돌을 확인한다. 외부 접근은 해당 주소 전용 HTTPS 프록시를 통한다.
- 수집기는 Linux에서 화면 없는 Chromium으로 실행한다. 원본 계정은 실행 환경변수로 주입하고 Mac의 기존 키체인 동작은 유지한다.
- `/data`는 영속 저장소다. 기존 SQLite DB 전체와 업로드를 보존하고, 컨테이너 교체 시 사라지는 파일시스템에 저장하지 않는다.
- 최초 웹 확인 단계에서는 수집기 프로필과 WARP 자동 전송을 끈다. DB 이전 및 로컬 수집기 종료 확인 후 수집기를 하나만 시작한다.
- 이미지 시작 시 seed나 `prisma db push`를 실행하지 않는다. 운영에 개발용 seed 계정을 생성하지 않는다.
- CI는 합성 데이터와 네트워크 없는 브라우저 확인에만 사용한다. AWS 권한과 운영 인증정보를 CI에 제공하지 않는다. CI 성공은 실제 원본 로그인 또는 운영 배포 성공을 뜻하지 않는다.

## 운영 담당자가 확정할 항목

1. 같은 서버에 추가 실행할 용량과 포트, 또는 승인된 대체 서버.
2. 최종 도메인, DNS, 인증서, 독립된 HTTPS 프록시 설정. 기존 WARP upstream은 유지한다.
3. 비공개 소스의 검토된 버전, Linux 이미지 빌드·검사·보관 경로, 승인된 배포/재시작 경로. 기존 WARP 역할의 신뢰 정책을 임의 확장하지 않는다.
4. 독립된 영속 디렉터리/볼륨과 비루트 프로세스 접근권한, 백업 및 복구 경로.
5. 기존 승인된 비밀 관리 체계를 통한 `AUTH_SECRET`, 원본 로그인 정보, `WARP_MARKETING_API_KEY` 주입. 값은 문서·GitHub·로그·명령 인자·배포 산출물에 넣지 않는다. WARP의 `/evn-warp/app-env` 전체를 읽어 Marketing에 복사하지 않는다.
6. 최종 이전 시각과 로컬 수집기 종료 담당자. 로컬/서버의 별개 DB는 서로의 잠금을 공유하지 않으므로 양쪽을 동시에 운영하지 않는다.

## 자료 이전 및 전환 순서

1. 합성 DB로 Linux 이미지, 비루트 실행, Chromium, 로그인 보호, 웹 재시작과 영속 저장을 확인한다. 서버 자원 측정과 담당자 검토를 완료한다.
2. 로컬 서비스가 정상인 상태에서 서버 웹·HTTPS 경로를 준비한다. 서버 수집기와 WARP 전송은 비활성으로 둔다. 공용 테스트 고객이나 임시 인증 우회 경로를 만들지 않는다.
3. 전환 시 로컬 수집기와 로컬 데이터 변경을 중지한다. 정상 종료와 활성 lease 해제를 확인한다. 강제 종료라면 기존 lease가 만료될 때까지 기다리고 DB를 임의로 수정하지 않는다.
4. Python SQLite backup API 등 일관된 백업 방식으로 SQLite 전체를 복사한다. WAL 사용 중인 `dev.db` 파일 하나를 단순 복사하지 않는다. 업로드도 같은 시점에 보존한다. 승인된 암호화 전송 경로로 이전하고 원본은 보관한다.
5. 이전 전후 무결성, 모든 업무 테이블 행 수, 문의 원본 식별값 및 전송 확인 이력의 동일성을 확인한다. 고객 원문이나 비밀번호 해시를 출력하지 않는다. 파일/행 비교 결과는 일치 여부와 집계만 기록한다. 기존 사용자 계정의 해시를 유지해 사용자가 기존 계정으로 로그인할 수 있게 한다.
6. 확인된 기준 스냅샷은 문의 409건 / WARP 전달 406건 / 연락처 충돌 보류 3건 / 사용자 1명이다. 실제 전환 시 다시 집계하며 이 숫자를 고정 기대값으로 사용하지 않는다. 기존 3개 Prisma migration ledger도 이전한다.
7. 승인된 환경값으로 서버 웹을 시작하고 HTTPS 로그인·문의 목록·전송 상태를 확인한다. 서버 수집기를 전송 비활성 상태로 시작해 원본 자동 로그인 및 신규 전용 수집을 먼저 확인한다. 정상적인 원본 변경 이외에 기존 수집 자료가 바뀌지 않았는지 확인한다.
8. WARP 연결 검사 후 검토된 방식으로 1건 등록·동일 원본 식별값 재전송의 중복 방지를 확인한다. 이미 전달 완료된 기록을 시험 목적으로 지우거나 고객을 새로 만들지 않는다. 기존 보류 3건은 대상 고객이 결정되기 전까지 유지한다.
9. WARP 자동 전송을 활성화하고 다음 1시간 주기의 실제 실행을 확인한다. 재시작 후 자동 복구와 로그인도 확인한다. 이 확인이 끝날 때까지 서버 상시 수집 완료라고 보고하지 않는다.

## 복구 및 완료 기준

- 서버 수집/등록 시작 전 실패: 서버 후보를 중지하고 로컬 원본을 그대로 재개한다.
- 서버에서 신규 수집/등록이 시작된 후 실패: 먼저 서버 수집기를 중지하고 최신 서버 DB·등록 확인 이력을 보존한다. 이전 로컬 DB로 바로 되돌아가 동시에 수집하지 않는다. 검증된 최신 상태를 단일 실행 위치로 이전한다.
- WARP의 배포·DB·트래픽 복구는 기존 담당자의 공식 release/rollback 절차를 따른다. Marketing 장애 해결을 이유로 WARP DB를 복원하거나 변경하지 않는다.
- 완료 증거: 검토된 소스/이미지 버전, 실제 HTTPS 주소, 계정 로그인, 이전 집계 일치, 원본 자동 로그인, 신규 수집, WARP 등록·중복 방지, 시간당 실행, 재시작 복구. 현재 이 문서는 그 완료 증거를 대신하지 않는다.
